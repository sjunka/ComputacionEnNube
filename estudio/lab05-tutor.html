Checkpoint Lab 2 · S05 Seguridad y gobernanza

Lab 05: permitido o denegado

Una sola idea: poder llegar no es poder hacer. La EC2 llega a S3 por la red, pero lo que puede leer o escribir lo decide la policy de su IAM Role.

1 · La cadena

Cinco preguntas, en este orden

Cada control responde una pregunta distinta. Ante un error, ubica en qué paso se rompió: el mensaje lo delata.

  1. ¿Puedo llegar?Red: route table, IP pública, DNSSi falla: se cuelga, timeout, «Could not connect to the endpoint URL».
  2. ¿Quién soy?Identidad: IAM Role vía instance profile → credenciales temporalesSi falla: «Unable to locate credentials». Evidencia: get-caller-identity muestra assumed-role/dcl-dev-role-s05/i-….
  3. ¿Qué puedo hacer?Autorización: policy = Effect + Action + ResourceSi falla: AccessDenied, rápido, con «no identity-based policy allows». Todo lo no permitido queda en deny implícito.
  4. ¿Está protegido el dato?Cifrado: SSE-S3 (AES256)Transparente para quien está autorizado. No decide quién lee.
  5. ¿Quién lo hizo?Trazabilidad: CloudTrail Event historyMuestra management events como AttachRolePolicy (userIdentity, eventTime). No previene nada. PutObject es un data event y no aparece ahí.
2 · Las pruebas del lab

Misma EC2, mismo role: solo una celda en verde

La policy concede únicamente s3:GetObject sobre allowed/*. Cambiar la Action o el Resource deja la petición fuera del permiso.

allowed/context.txtrestricted/secret.txt
GetObject PASSPrueba que red, DNS e identidad funcionan. AccessDeniedPor Resource: fuera de allowed/*.
PutObject AccessDeniedPor Action: no hay s3:PutObject. AccessDeniedFalla Action y Resource.

Frase para la demo: «misma red, mismo role; cambia solo Resource o Action, así que es autorización y no reachability». Nunca se «arregla» con s3:* o FullAccess: eso destruye la prueba.

¿Qué evidencia demuestra que el AccessDenied es autorización y no red?

Desde la misma EC2 y con el mismo ARN de assumed-role, el GetObject sobre allowed/ funciona: la ruta, el DNS y las credenciales están bien. El objeto restricted existe. El error aparece solo al cambiar el Resource o la Action, y el mensaje dice «no identity-based policy allows». La policy visible coincide con ese límite.

¿Por qué SSE-S3 no sustituye a IAM, ni CloudTrail a los controles preventivos?

SSE-S3 protege el dato en disco y es transparente para quien está autorizado: no decide quién lee. CloudTrail registra después quién hizo qué, pero no impide nada. Cada control responde una pregunta distinta: si puedo llegar, quién soy, qué puedo hacer, si el dato está protegido y quién lo hizo.

Checkpoint Lab 2 · S06 Operación y automatización

Lab 06: desplegado no es operable

Una sola idea: CREATE_COMPLETE solo dice que CloudFormation terminó. Que el sistema se comporta lo prueba una cadena con timestamps: carga → métrica → condición → alarma.

1 · La cadena

Seis pasos, del template al delete

Los dos primeros son despliegue y los del 3 al 4 son observación. Separarlos es la mitad del troubleshooting.

  1. Declarar el estado deseadoTemplate YAML: SG + EC2 + alarma, con parámetros (VpcId, SubnetId, CpuThreshold, LabRevision)Template válido no es infraestructura desplegada. No crea IAM ni toca el baseline.
  2. MaterializarloStack → CREATE_COMPLETE · logical ID → physical IDSi falla: los Events del stack (CREATE_FAILED / ROLLBACK) dicen qué recurso y por qué. Orden por dependencias: SG → EC2 → alarma.
  3. Producir la señalUser data: 2 procesos while :; do :; done, 900 s → AWS/EC2 CPUUtilizationBasic monitoring: un datapoint cada 5 min, publicado por el hipervisor (sin agente ni IP pública).
  4. Evaluar la condiciónAlarma: Average ≥ 70%, periodo 300 s, 2 de 2 datapointsEstados: INSUFFICIENT_DATA (sin datos suficientes) → OK → ALARM. ALARM dice que la condición se cumplió, no cuál es la causa raíz.
  5. Cambiar de forma declarativaUpdate LabRevision v1 → v2 (change set: Replacement False)UPDATE_COMPLETE no basta. La prueba es el mismo InstanceId antes y después, y el tag en v2.
  6. Cerrar el ciclo de vidaDelete stack → DELETE_COMPLETEEl stack sabe qué creó y lo borra en orden inverso. El baseline no es suyo y no se toca.

¿Qué evidencia distingue un problema de despliegue de uno de observación?

Despliegue: los Events del stack muestran CREATE_FAILED o ROLLBACK con la causa (template, permisos, parámetros, quota). Observación: el stack está completo y los recursos existen, pero la métrica no tiene datapoints, la dimensión InstanceId no coincide, o todavía no se cumplen el periodo y la regla de 2 de 2.

¿Por qué el cleanup se hace con Delete stack y no borrando recursos uno por uno?

El stack es la unidad de ciclo de vida: sabe qué creó y en qué orden borrarlo. Borrar a mano deja el stack inconsistente y puede llevar a DELETE_FAILED. El EBS se va con la EC2 por DeleteOnTermination, y el baseline S01 no se toca porque no es parte del stack.

Checkpoint Lab 2 · S07 Modernización

Lab 07: la frontera se mueve

Una sola idea: serverless transfiere el servidor, no la responsabilidad. AWS se queda con la VM, el SO y la capacidad. Tú sigues a cargo de los permisos, el código, los eventos, los logs y el costo.

1 · La cadena

Objeto → evento → invocación → log

«La Lambda existe» no prueba nada. La evidencia une los cinco pasos con el mismo key.

  1. ProductorObjeto nuevo incoming/order-001.json en un bucket privadoSe crea después del trigger: las notificaciones no son retroactivas. Un Test manual prueba el código, no la integración.
  2. EventoNotificación s3:ObjectCreated:* con prefix incoming/ y suffix .jsonSi el key no cumple el filtro, no hay invocación. La entrega es at-least-once: puede haber duplicados.
  3. Permiso para invocarResource-based policy de la función: s3.amazonaws.com → lambda:InvokeFunction, SourceArn = el bucketSin este permiso, S3 rechaza la notificación: «Unable to validate the following destination configurations».
  4. EjecuciónLambda Python 3.14 con execution role mínimo: solo logs:CreateLogStream y logs:PutLogEventsSin permisos de S3: bucket y key llegan dentro del evento. El log group se crea antes para no conceder CreateLogGroup.
  5. EvidenciaCloudWatch Logs: línea JSON con bucket, key, eventName y requestIdSi ejecuta y no hay log: execution role, log group, timestamp. Si el key no coincide: URL encoding (unquote_plus).

¿Qué evidencia demuestra que el problema está en la integración y no en la existencia de la función?

La función existe y su Test manual funciona, así que el código y el role de logs están bien. El objeto existe con el key esperado y se creó después del trigger. Pero Invocations = 0 y no hay log stream nuevo. Entonces la falla está entre S3 y Lambda: la notificación del bucket, el prefix o suffix frente al key real, la región o la resource-based policy.

¿Qué responsabilidades se transfirieron a AWS y cuáles siguen siendo del equipo?

Se transfieren el servidor, el SO y sus parches, el runtime administrado, el escalado por invocación, la disponibilidad multi-AZ y el costo en reposo. Siguen siendo del equipo el execution role y la resource-based policy, el código y el manejo de eventos (URL encoding, duplicados, evitar recursión), el filtro del trigger, los logs y el costo por invocación. La complejidad no desaparece: se mueve a permisos, eventos y observabilidad.
